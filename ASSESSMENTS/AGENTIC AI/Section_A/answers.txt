SECTION A — CONCEPT APPLICATION

A1. For this use case I recommend a hybrid: retrieve current restaurant menus/availability and user-approved dietary/order preferences with RAG or structured database/API tools, then use prompt engineering to enforce dietary safety, clarify ambiguity, and format personalized recommendations. Daily-changing menu facts belong in the live source of truth; putting them into model weights would make them stale. Fine-tuning may help with a stable food-service tone or domain-specific intent classification, but it is optional and cannot guarantee current availability or reliably encode every user's unique constraints.

A2. Full fine-tuning updates the base model's weights, which requires storing gradients and optimizer states for a very large number of parameters. LoRA freezes the pretrained weights and trains small low-rank adapter matrices inserted into selected layers, so the trainable state and optimizer memory are much smaller and an 8 GB GPU may be enough for a suitably small/quantized model, sequence length, and batch size. The trade-off is less adaptation capacity and dependence on the base model; adapters may underperform full tuning on a large, broad shift and multiple adapters add deployment/management overhead. VRAM fit must still be measured for the chosen model.

A3. Limitation 1: fine-tuning reflects its training distribution, so it may fail on rare or novel complaint wording/events; collect representative, consented examples and re-tune/evaluate if the issue is recurring and stable. Limitation 2: fine-tuning stores behavioral/statistical patterns in weights, not a reliable live fact store, and adding examples cannot guarantee exact factual recall or freshness; use RAG for changing policy/event facts when authoritative, searchable documents exist, or few-shot examples for a narrow temporary format/labeling task when context budget permits. Sensitive or high-impact cases need escalation rules and human review, not just a new model.

A4. PERCEIVE: extract item=2 Masala Dosa, restaurant=Saravana Bhavan, requested delivery=7 PM tonight; identify missing delivery address, city/time zone, and whether “tonight” maps to the intended local date. THINK: ask for missing address/date if not in trusted profile; validate dietary/allergy constraints; plan restaurant availability → menu/price → delivery-slot/ETA checks; do not assume the restaurant or slot is available. ACT: call check_restaurant_status(name, location, date); if open call search_menu(name,item) and check_delivery_slot(location,7 PM); show price/ETA and draft cart; ask the customer to confirm before place_order. OBSERVE each result, verify item/quantity/slot, then continue. If the restaurant is unavailable, observe that result, search nearby alternatives or another slot, present options, and ask the user which to choose; never silently substitute or order.

A5. Expose read-only tools such as list_tables (limited to approved views), describe_table (column allowlist), get_order_status(order_id), get_delivery_eta(order_id), and run_select_query with validated SELECT-only SQL, row limits, timeouts, and approved columns. Avoid arbitrary write access because analysts/support need answers, while changes to orders/payments need a separate audited service and human authorization. A support question: “What is the latest status and ETA for order FD4521?” Use database views that omit phone, address, and payment data; enforce least-privilege DB credentials, column allowlists, parameter binding, row limits, result redaction, and audit logs. The LLM should never receive columns its request does not need.

A6. Cycle 1 — Reason summary: verify the order and delivery events before making a financial decision. Action: lookup_order_status(FD4521). Observation: order delivered 40 minutes late; courier event log confirms 40-minute delay. Cycle 2 — Reason summary: verify cold-food complaint evidence and policy eligibility; do not promise an amount before policy returns. Action: check_refund_eligibility(FD4521, issue='late and cold'). Observation: policy returns eligible for a partial refund or capped credit, not an automatic full refund. Final response explains the verified options and asks which the user prefers; apply a credit only after policy and required approval. Separating reasoning summaries from actions allows validation and policy checks before a consequential refund/discount, makes tool errors visible, and provides an audit trail.
